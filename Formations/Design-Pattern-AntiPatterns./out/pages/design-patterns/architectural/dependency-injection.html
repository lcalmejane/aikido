💉 Dependency Injection Pattern

Inverser le contrôle des dépendances pour une meilleure flexibilité

🏗️ Architectural
⭐ Difficulté: Intermédiaire

🔄 Inversion de Contrôle

🎯 Définition

Le Dependency Injection est un pattern architectural qui inverse le contrôle en injectant les dépendances depuis l'extérieur. Les classes déclarent leurs besoins sans les créer, permettant une flexibilité maximale et des tests simplifiés.

❌ Problème Résolu

  • Couplage fort entre classes et dépendances
  • Tests difficiles avec dépendances réelles
  • Modifications en cascade lors de changements
  • Instanciation manuelle complexe

✅ Solution Apportée

  • Inversion de contrôle des dépendances
  • Injection automatique via conteneur DI
  • Tests facilités avec mocks et stubs
  • Configuration centralisée flexible
💡 Principe clé : Ne pas créer ses dépendances mais les recevoir de l'extérieur, permettant l'inversion de contrôle et une architecture découplée.

💡 Point clé : Le conteneur DI gère automatiquement la création et l'injection des dépendances, permettant une configuration centralisée et flexible.

💻 Implémentations

Exemple : Système de notification avec DI

// Interface pour les services de notification
interface NotificationService {
    send(message: string, recipient: string): Promise<boolean>;
}

// Implémentations concrètes
class EmailService implements NotificationService {
    async send(message: string, recipient: string): Promise<boolean> {
        console.log(`📧 Email envoyé à ${recipient}: ${message}`);
        return new Promise(resolve => setTimeout(() => resolve(true), 100));
    }
}

class SMSService implements NotificationService {
    async send(message: string, recipient: string): Promise<boolean> {
        console.log(`📱 SMS envoyé à ${recipient}: ${message}`);
        return new Promise(resolve => setTimeout(() => resolve(true), 50));
    }
}

// Client qui utilise l'injection de dépendance
class NotificationManager {
    constructor(
        private emailService: NotificationService,
        private smsService: NotificationService
    ) {}

    async sendWelcomeMessage(userEmail: string, userPhone: string): Promise<void> {
        const message = "Bienvenue sur notre plateforme !";
        
        await Promise.all([
            this.emailService.send(message, userEmail),
            this.smsService.send(message, userPhone)
        ]);
        
        console.log("✅ Message de bienvenue envoyé");
    }
}

// Conteneur d'injection de dépendance
class DIContainer {
    private bindings = new Map<string, any>();
    private instances = new Map<string, any>();

    bind<T>(token: string, implementation: new (...args: any[]) => T): void {
        this.bindings.set(token, implementation);
    }

    resolve<T>(token: string): T {
        if (this.instances.has(token)) {
            return this.instances.get(token);
        }

        const Implementation = this.bindings.get(token);
        if (!Implementation) {
            throw new Error(`No binding found for ${token}`);
        }

        const instance = new Implementation();
        this.instances.set(token, instance);
        return instance;
    }

    createNotificationManager(): NotificationManager {
        return new NotificationManager(
            this.resolve<NotificationService>('EmailService'),
            this.resolve<NotificationService>('SMSService')
        );
    }
}

// Configuration et utilisation
const container = new DIContainer();
container.bind('EmailService', EmailService);
container.bind('SMSService', SMSService);

const notificationManager = container.createNotificationManager();

// Conteneur d'injection de dépendance
class DIContainer {
    private array $bindings = [];
    
    public function bind(string $abstract, callable $concrete): void {
        $this->bindings[$abstract] = $concrete;
    }
    
    public function resolve(string $abstract) {
        if (isset($this->bindings[$abstract])) {
            return $this->bindings[$abstract]();
        }
        
        throw new Exception("No binding found for {$abstract}");
    }
}

    return new PaymentService($container->resolve('PaymentProcessor'));
});

// Interface pour les stratégies de cache
interface CacheStrategy {
    void put(String key, Object value);
    Object get(String key);
    void clear();
}

// Implémentations concrètes
class MemoryCache implements CacheStrategy {
    private final Map<String, Object> cache = new HashMap<>();
    
    @Override
    public void put(String key, Object value) {
        cache.put(key, value);
        System.out.println("🧠 Mise en cache mémoire: " + key);
    }
    
    @Override
    public Object get(String key) {
        Object value = cache.get(key);
        System.out.println("🔍 Lecture cache: " + key + 
                          (value != null ? " (trouvé)" : " (non trouvé)"));
        return value;
    }
    
    @Override
    public void clear() {
        cache.clear();
        System.out.println("🧹 Cache vidé");
    }
}

class RedisCache implements CacheStrategy {
    private final String host;
    private final Map<String, Object> mockRedis = new HashMap<>();
    
    public RedisCache(String host) {
        this.host = host;
        System.out.println("🔗 Connexion Redis: " + host);
    }
    
    @Override
    public void put(String key, Object value) {
        mockRedis.put(key, value);
        System.out.println("📡 Mise en cache Redis: " + key);
    }
    
    @Override
    public Object get(String key) {
        Object value = mockRedis.get(key);
        System.out.println("📡 Lecture Redis: " + key + 
                          (value != null ? " (trouvé)" : " (non trouvé)"));
        return value;
    }
    
    @Override
    public void clear() {
        mockRedis.clear();
        System.out.println("📡 Cache Redis vidé");
    }
}

// Service utilisant l'injection de dépendance
class CacheService {
    private final CacheStrategy cache;
    
    public CacheService(CacheStrategy cache) {
        this.cache = cache;
    }
    
    public void store(String key, Object value) {
        cache.put(key, value);
    }
    
    public Object retrieve(String key) {
        return cache.get(key);
    }
    
    public void clearAll() {
        cache.clear();
    }
}

// Conteneur d'injection simple
class DIContainer {
    private final Map<Class<?>, Supplier<?>> factories = new HashMap<>();
    
    public <T> void register(Class<T> type, Supplier<T> factory) {
        factories.put(type, factory);
    }
    
    @SuppressWarnings("unchecked")
    public <T> T resolve(Class<T> type) {
        Supplier<?> factory = factories.get(type);
        if (factory == null) {
            throw new IllegalArgumentException("No factory for " + type.getName());
        }
        return (T) factory.get();
    }
}

// Utilisation
public class DIExample {
    public static void main(String[] args) {
        DIContainer container = new DIContainer();
        
        // Configuration
        container.register(CacheStrategy.class, () -> new MemoryCache());
        container.register(CacheService.class, () -> 
            new CacheService(container.resolve(CacheStrategy.class)));
        
        // Utilisation
        CacheService service = container.resolve(CacheService.class);
        service.store("user:123", "John Doe");
        service.retrieve("user:123");
    }
}

⚖️ Avantages et Inconvénients

✅ Avantages

  • Faible couplage : Classes indépendantes de leurs dépendances concrètes
  • Testabilité excellente : Injection de mocks et stubs facilement
  • Flexibilité maximale : Changement d'implémentation sans modification du code
  • Principe SOLID : Respect de l'inversion de dépendance
  • Configuration centralisée : Gestion des dépendances en un point

❌ Inconvénients

  • Complexité initiale : Configuration du conteneur DI
  • Courbe d'apprentissage : Concepts d'inversion de contrôle
  • Debugging difficile : Flux d'exécution moins évident
  • Performance : Overhead de résolution des dépendances
  • Over-engineering : Peut être excessif pour des projets simples

🎯 Cas d'usage recommandés

✅ Recommandé pour

  • Applications avec nombreuses dépendances inter-services
  • Projets nécessitant des tests unitaires extensifs
  • Architectures modulaires et extensibles
  • Applications avec configurations multiples (dev/prod)
  • Systèmes nécessitant le changement d'implémentations

❌ Éviter pour

  • Applications simples avec peu de dépendances
  • Prototypes rapides ou scripts utilitaires
  • Équipes non familières avec les concepts DI
  • Applications avec cycle de vie simple des objets
  • Projets avec contraintes de performance strictes

🎮 Exercice pratique

Scénario : Système de commande e-commerce

Vous développez un système de traitement de commandes avec les composants suivants :

  • Service de validation des commandes
  • Service de calcul des prix (avec taxes et remises)
  • Service de gestion des stocks
  • Service de notification client
  • Service de paiement (multiple providers)

Question : Quel est le principal avantage de l'injection de dépendance dans ce contexte ?

✅ Excellente réponse !

La facilitation des tests unitaires est effectivement l'un des principaux avantages de DI. Elle permet :

  • Injection de mocks pour isoler les composants testés
  • Tests indépendants des services externes (base de données, APIs)
  • Simulation de différents scénarios (succès, échecs, timeouts)
  • Tests rapides sans dépendances lourdes

Dans votre système e-commerce, vous pourriez tester le service de commande en injectant des mocks pour le paiement, les stocks, et les notifications, permettant de tester chaque composant isolément.

❌ Incorrect

L'injection de dépendance peut en fait introduire un léger overhead de performance à cause de la résolution des dépendances. L'amélioration des performances n'est pas son objectif principal.

🤔 Pas tout à fait

L'injection de dépendance ne réduit pas le nombre de classes. Au contraire, elle encourage souvent la création d'interfaces et peut augmenter le nombre de classes pour une meilleure séparation des responsabilités.

🤔 Partiellement correct

Bien que DI puisse clarifier les dépendances d'une classe, elle ne simplifie pas directement la logique métier. Elle se concentre plutôt sur la gestion des dépendances et l'inversion de contrôle.
