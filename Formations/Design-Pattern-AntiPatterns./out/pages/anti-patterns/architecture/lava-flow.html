🌋 Lava Flow

L'anti-pattern du code fossilisé

🦨 Anti-pattern architectural critique
⏱️ ~35 minutes
🎯 Nettoyage sécurisé essentiel
🧩 6 biais cognitifs liés

🎯 Définition

Le Lava Flow est un anti-pattern qui décrit l'accumulation de code mort, obsolète ou expérimental qui reste dans le système parce que personne n'ose le supprimer, créant une "coulée de lave" figée dans le temps.

❌ Problèmes Causés

  • Code inutilisé qui encombre la base de code
  • Confusion pour les nouveaux développeurs
  • Maintenance de code sans valeur ajoutée
  • Risques de sécurité (endpoints de debug oubliés)
  • Performance dégradée par du code mort

✅ Solutions Apportées

  • Analyse automatique du code mort
  • Nettoyage progressif et sécurisé
  • Outils de détection intégrés au CI/CD
  • Stratégies de dépréciation contrôlée
  • Prévention par bonnes pratiques
⚠️ Attention : Le code mort peut contenir des failles de sécurité et ralentir significativement le développement et la maintenance.

Caractéristiques du Lava Flow

💀
Code inutilisé

Fonctions, classes ou modules non appelés

🧪
Code expérimental

Prototypes abandonnés mais conservés

😰
Peur de supprimer

Incertitude sur l'impact de la suppression

📚
Documentation manquante

Absence d'explication sur l'utilité

🧠 Biais Cognitifs Associés

Le Lava Flow résulte de plusieurs biais cognitifs qui nous empêchent de nettoyer le code obsolète :

😰

Loss Aversion

Manifestation : "Et si ce code servait à quelque chose d'important ?"

Peur de perdre quelque chose d'important en supprimant du code, même quand il semble inutilisé depuis longtemps.

Exemple : Conserver une ancienne API "au cas où" un client l'utiliserait encore, sans vérifier réellement.
🤷‍♂️

Uncertainty Avoidance

Manifestation : "Je ne sais pas ce que fait ce code, mieux vaut le garder"

Évitement des situations incertaines, préférence pour maintenir le statu quo plutôt que de prendre des risques.

Exemple : Garder du code non documenté par peur qu'il ait une fonction cachée importante.
👥

Diffusion of Responsibility

Manifestation : "Ce n'est pas à moi de supprimer ce code"

Dilution de la responsabilité dans un groupe où personne ne prend l'initiative de nettoyer le code mort.

Exemple : Code mort qui persiste car chaque développeur pense que c'est à quelqu'un d'autre de s'en occuper.
💰

Sunk Cost Fallacy

Manifestation : "J'ai passé des heures sur ce code, je ne peux pas le jeter"

Réticence à abandonner quelque chose dans lequel on a investi du temps et des efforts, même si ce n'est plus utile.

Exemple : Conserver un prototype expérimental raté parce qu'il a demandé beaucoup de travail.
🔮

Just-in-Case Thinking

Manifestation : "On pourrait en avoir besoin un jour"

Conservation "au cas où" on en aurait besoin plus tard, sans évaluation objective de la probabilité d'usage futur.

Exemple : Garder du code de secours ou des fonctionnalités expérimentales "pour plus tard".
⏰

Time Pressure Bias

Manifestation : "Pas le temps de nettoyer, il faut livrer"

Sous pression temporelle, tendance à ajouter du code sans prendre le temps de nettoyer l'existant.

Exemple : Accumulation continue de code sans phase de nettoyage planifiée dans les sprints.

        // Logique actuelle...
        return $this->saveUser($userData);

        // Cette méthode était utilisée avant la refactorisation
        // Personne n'ose la supprimer "au cas où"
        $user = new User();
        $user->name = $userData['name'];
        $user->email = $userData['email'];
        // Logique obsolète...
        return $user;
    }

    public function createUserWithAI($userData) {
        // Expérimentation avec IA pour validation
        // Jamais terminé, jamais utilisé, mais conservé

        if ($aiValidator->validate($userData)) {
            return $this->createUser($userData);
        }
        throw new Exception('AI validation failed');
    }

        // Utilisée pendant le développement
        // Oubliée en production
        error_log("Creating user: " . print_r($userData, true));
        var_dump($userData);
        die("Debug stop");
    }
    
    // LAVA FLOW: Code commenté "au cas où"
    public function updateUser($id, $userData) {
        $user = $this->findUser($id);
        
        // Ancienne logique de validation (commentée mais conservée)

        */

        // Version intermédiaire

        return ResponseEntity.ok(order);
    }
    
    // LAVA FLOW: Endpoint expérimental

        // Endpoint de test créé pendant le développement

        if (!$user) {

     * 
     * @param int $id ID de l'utilisateur

OrderController.java - Version Propre Java 

package com.example.controllers;

import com.example.dto.OrderRequest;
import com.example.dto.OrderResponse;
import com.example.models.Order;
import com.example.services.OrderService;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import javax.validation.Valid;

/**
 * Contrôleur REST pour la gestion des commandes
 * 
 * @version 3.0.0
 * @since 2024-01-15
 * @author Équipe Backend
 */
@RestController
@RequestMapping("/api/v3/orders")
public class OrderController {
    
    private final OrderService orderService;
    
    @Autowired
    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }
    
    /**
     * Crée une nouvelle commande
     * 
     * @param request Données de la commande
     * @return La commande créée
     */
    @PostMapping
    public ResponseEntity createOrder(@Valid @RequestBody OrderRequest request) {
        Order order = orderService.createOrder(request);
        OrderResponse response = OrderResponse.fromOrder(order);
        return ResponseEntity.ok(response);
    }
    
    /**
     * Récupère une commande par son ID
     * 
     * @param id ID de la commande
     * @return La commande trouvée
     */
    @GetMapping("/{id}")
    public ResponseEntity getOrder(@PathVariable Long id) {
        Order order = orderService.findById(id);
        OrderResponse response = OrderResponse.fromOrder(order);
        return ResponseEntity.ok(response);
    }
    
    /**
     * Met à jour une commande existante
     * 
     * @param id ID de la commande
     * @param request Nouvelles données
     * @return La commande mise à jour
     */
    @PutMapping("/{id}")
    public ResponseEntity updateOrder(
        @PathVariable Long id, 
        @Valid @RequestBody OrderRequest request
    ) {
        Order order = orderService.updateOrder(id, request);
        OrderResponse response = OrderResponse.fromOrder(order);
        return ResponseEntity.ok(response);
    }
    
    /**
     * Supprime une commande
     * 
     * @param id ID de la commande à supprimer
     * @return Confirmation de suppression
     */
    @DeleteMapping("/{id}")
    public ResponseEntity deleteOrder(@PathVariable Long id) {
        orderService.deleteOrder(id);
        return ResponseEntity.noContent().build();
    }
}

🧹 Techniques de Nettoyage

Stratégies pour identifier et supprimer le code mort en toute sécurité :

🔍

Static Analysis

Utiliser des outils d'analyse statique pour détecter le code inutilisé

Outils :
  • SonarQube - Analyse complète de qualité
  • PMD/SpotBugs - Détection Java
  • ESLint - Code JavaScript mort
  • Psalm/PHPStan - Analyse PHP
Avantages : Détection automatique, rapports détaillés
📊

Code Coverage Analysis

Analyser la couverture de code pour identifier les parties non testées/utilisées

Étapes :
  1. Exécuter la suite de tests complète
  2. Générer le rapport de couverture
  3. Identifier les zones à 0% de couverture
  4. Analyser si c'est du code mort ou manque de tests
Avantages : Données objectives, identification précise
🎯

Feature Flagging

Désactiver progressivement les fonctionnalités obsolètes avant suppression

Processus :
  1. Identifier le code potentiellement mort
  2. Ajouter des feature flags pour le désactiver
  3. Monitorer l'impact pendant une période
  4. Supprimer définitivement si aucun impact
Avantages : Suppression sécurisée, rollback possible
📈

Usage Monitoring

Surveiller l'utilisation réelle du code en production

Métriques :
  • Logs d'accès aux endpoints
  • Métriques d'appels de méthodes
  • Traces d'exécution
  • Analytics d'utilisation
Avantages : Données réelles d'usage, décisions éclairées
🔄

Gradual Deprecation

Processus de dépréciation progressive et contrôlée

Phases :
  1. Marquer @Deprecated avec date limite
  2. Ajouter des warnings dans les logs
  3. Communiquer aux équipes utilisatrices
  4. Supprimer après période de grâce
Avantages : Transition douce, communication claire
🧪

Safe Deletion Testing

Tests de suppression sécurisée avec rollback

Stratégie :
  1. Créer une branche de test
  2. Supprimer le code suspect
  3. Exécuter tous les tests
  4. Tester en environnement de staging
  5. Merger si aucun problème
Avantages : Validation complète, risque minimal

🎯 Exercices Pratiques

Mettez en pratique les techniques de détection et nettoyage du code mort :

1

Détection de Code Mort

🟡 Intermédiaire

Analysez une base de code existante pour identifier le code mort en utilisant des outils d'analyse statique.

Objectifs :
  • Configurer SonarQube ou un outil équivalent
  • Identifier les méthodes et classes inutilisées
  • Analyser les imports et dépendances mortes
  • Générer un rapport de nettoyage prioritaire
Étapes :
  1. Choisir un projet existant (ou utiliser le projet fourni)
  2. Installer et configurer SonarQube
  3. Exécuter l'analyse complète
  4. Examiner les règles "Dead Code" et "Unused"
  5. Prioriser les éléments à nettoyer
  6. Créer un plan de nettoyage progressif
Validation :
  • ✅ Rapport SonarQube généré avec métriques de code mort
  • ✅ Liste priorisée des éléments à supprimer
  • ✅ Plan de nettoyage avec timeline
2

Nettoyage Sécurisé

🔴 Avancé

Implémentez une stratégie de nettoyage sécurisé avec feature flags et monitoring pour supprimer du code mort sans risque.

Objectifs :
  • Implémenter des feature flags pour désactivation progressive
  • Ajouter du monitoring sur le code à supprimer
  • Créer des tests de régression
  • Documenter le processus de rollback
Étapes :
  1. Identifier une fonctionnalité potentiellement morte
  2. Ajouter des feature flags pour la contrôler
  3. Implémenter du logging/monitoring sur son usage
  4. Désactiver progressivement (dev → staging → prod)
  5. Monitorer pendant 2 semaines minimum
  6. Supprimer définitivement si aucun usage détecté
Validation :
  • ✅ Feature flags fonctionnels avec rollback
  • ✅ Monitoring en place avec alertes
  • ✅ Tests de régression passants
  • ✅ Documentation du processus
3

Stratégie de Prévention

🟡 Intermédiaire

Mettez en place des processus et outils pour prévenir l'accumulation future de code mort.

Objectifs :
  • Configurer des checks automatiques dans le CI/CD
  • Établir des règles de review de code
  • Créer des métriques de suivi
  • Former l'équipe aux bonnes pratiques
Étapes :
  1. Intégrer l'analyse de code mort dans le pipeline CI/CD
  2. Configurer des seuils d'alerte pour les métriques
  3. Créer des templates de PR avec checklist anti-lava-flow
  4. Planifier des sessions de nettoyage régulières
  5. Documenter les guidelines de l'équipe
  6. Mettre en place des revues de code focalisées
Validation :
  • ✅ Pipeline CI/CD avec checks de code mort
  • ✅ Métriques de suivi configurées
  • ✅ Guidelines d'équipe documentées
  • ✅ Processus de review adapté
